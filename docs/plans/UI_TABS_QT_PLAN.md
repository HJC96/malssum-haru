## 1. 이번 작업의 목표

사용자는 한 페이지에 QT와 일독 계획이 길게 이어지는 화면을 `오늘의 QT`와 `일독 계획` 두 탭으로 나누길 요청했다. 디자인은 `/Users/hanjichan/Desktop/git/omalssum-react`를 참고한다. 추가로 현재 QT 카드가 모두 “자동 확인 안 함”으로 나오고 오늘 장절을 표시하지 않는 문제도 해결한다.

여기서 서비스 분리는 **같은 웹 앱 안의 화면 분리**다. 별도 배포, MSA 서비스 추가, 로그인, 새 라우터 도입은 이 작업에 필요하지 않다. T20 Spring Cloud 실습은 별도 과제로 유지한다.

사용자가 말한 “오늘 큐티 본문”은 앞서 확정한 범위에 따라 **오늘 읽을 성경 책·장·절 범위**로 해석한다. 확인된 장절과 공식 링크를 보여 주고 성경 전문은 제공처에서 읽는다. 본문 뷰어·AI 생성 기능 추가는 이번 계획에 포함하지 않는다.

## 3. 목표 화면과 동작

```text
말씀하루                                  한국어 / English

                [ 오늘의 QT ] [ 일독 계획 ]

선택한 탭의 내용만 표시
  오늘의 QT: 제공처별 오늘 장절 · 날짜 · 상태 · 공식 링크
  일독 계획: 계획 입력 → 결과/진행률 → 목록·캘린더 → 내보내기

데이터 출처·라이선스
```

### 3.1 탭 계약

1. 첫 진입과 새로고침은 `오늘의 QT`. 탭 상태는 현재 메모리에만 유지한다.
2. 표시명은 한국어 `오늘의 QT` / `일독 계획`, 영어 `Today's QT` / `Reading plan`.
3. 한 번에 하나의 패널만 보인다. 비활성 패널은 스크롤 높이를 차지하지 않고 키보드·스크린리더 탐색에서도 빠진다.
4. 두 패널은 처음부터 마운트하고 `hidden`으로 전환한다. 일독 컴포넌트에 탭·언어에 따라 바뀌는 `key`를 주지 않는다.
5. 일독 입력, 계산 결과, 목록/캘린더 보기, 선택한 월, 내보내기 범위는 탭 왕복 후 유지한다. 새로고침 후에는 현재 비저장 정책대로 초기화한다.
6. 탭 이동·언어 변경으로 QT 요청이 매번 다시 발생하면 안 된다. 기존 캐시·재시도·서울 자정 처리를 유지한다.
7. QT 탭으로 돌아올 때 서울 날짜를 즉시 재평가한다. 오래된 범위를 오늘로 잠깐 표시하지 말고 기존 “다시 확인 중” 흐름으로 연결한다. 서버 날짜가 틀리거나 아직 오늘 자료가 없으면 공식 링크로 안내한다.
8. 계획이 길어도 서비스 전환을 찾기 쉽게 탭 줄을 작은 sticky 영역으로 둔다. 제목·언어 선택·탭이 모바일에서 겹치지 않게 하고 탭 전환 시 새 패널 상단을 볼 수 있게 한다. 강제 애니메이션이나 패널별 내부 스크롤은 도입하지 않는다.

권장 구조: `Shell`에 `type ServiceTab = 'qt' | 'plan'` 및 `activeTab` 상태, 새 `ServiceTabs.tsx`에는 선택·키보드 인터랙션만 둔다. 계산/데이터 로직은 기존 컴포넌트에 남긴다.

공유 DOM 계약:

| 요소 | 식별자/규칙 |
| --- | --- |
| 탭 줄 | `.service-tabs`, `role="tablist"`, 번역된 접근성 이름 |
| 버튼 | `.service-tabs__tab`, `role="tab"`, `id="service-tab-qt|plan"` |
| 연결 | `aria-controls="service-panel-qt|plan"`, `aria-selected` |
| 패널 | `.service-panel`, `role="tabpanel"`, `id="service-panel-qt|plan"`, `aria-labelledby` |
| 숨김 | 패널의 `hidden` + `.service-panel[hidden] { display: none !important; }` |

화살표 좌/우 및 Home/End로 탭 포커스 이동, Enter/Space 또는 클릭으로 선택하는 수동 활성화 방식을 사용한다. 탭 버튼은 roving tabindex로 탭 줄 전체가 Tab 키 한 정거장이 되게 한다. 패널 진입 경로, skip link, 포커스 표시를 유지한다.

### 3.2 디자인 참고와 적용 범위

참조 앱은 연한 배경 위 둥근 흰색 카드, 옅은 블루 헤더, 인디고 pill 버튼, 부드러운 그림자가 특징이다. 원본은 단일 `max-w-md` 카드에 큰 정사각형 이미지와 중앙 정렬 텍스트가 있는 구조다.

| 참조 근거 | 말씀하루에 적용할 방향 |
| --- | --- |
| `bg-gray-100`, `bg-white`, `bg-blue-50` | 연한 쿨 그레이 페이지 + 흰 카드 + 옅은 블루 강조 영역 |
| `rounded-3xl`, `shadow-lg`, `border-gray-200` | 카드 모서리 20~24px, 얇은 경계, 절제한 그림자 |
| 인디고 계열 `rounded-full` 버튼 | 선택 탭과 주요 동작에 인디고 pill 스타일 |
| `p-6` 및 간결한 제목/본문 구획 | 카드 안 여백 16px(모바일)/24px(넓은 화면), 설명 중복 최소화 |
| Gowun Dodum 설정 및 Google Fonts 로딩 | 첫 구현은 기존 시스템 폰트 유지. 폰트 자체 도입은 로컬 자산·라이선스·번들 검토 후 별도 결정 |
| 1:1 이미지, 외부 이미지 URL | 이번 UI에는 추가하지 않음. 현재 과제인 세로 길이 감소를 우선 |
| 무작위 성경 API, 가상 묵상/기도문 버튼 | 기능은 가져오지 않음. 기존 QT 계약과 기능을 사용 |

초기 색상 제안(사용자의 별도 확정값이 아닌 구현 기본안): `--bg: #f3f4f6`, `--surface: #ffffff`, `--surface-soft: #eff6ff`, `--accent: #4f46e5`, hover `#4338ca`, 본문 `#1f2937`, 보조문구 `#4b5563`. 실제 색 대비를 확인해 조정한다. 기존 dark theme, 상태 색, reduced-motion, forced-colors 대응도 유지한다.

- 스타일은 기존 CSS 토큰으로 구현한다. 참고 앱의 Tailwind/CRA 빌드 구성을 가져오지 않는다.
- 앱의 최대 너비는 기존 64rem 수준을 유지한다. 좁은 화면은 1열, 충분한 너비에서는 두 QT 카드를 나란히 배치한다. 일독 입력과 표는 읽기 쉬운 너비를 확보한다.
- 날짜·범위·상태·공식 링크 순서로 QT 카드의 정보 위계를 정한다. 긴 안내문을 카드마다 반복하지 않고 공통 안내로 묶을 수 있으나 제공처별 실패 사유는 남긴다.
- 일독 기본 입력과 계산 결과를 카드로 구분한다. 데이터가 잠정이라는 안내는 유지하고 세부 버전/장절 기준은 기존 상세 안내와 함께 정리할 수 있다. 필드 삭제·계산 방식 변경·추가 다단계 wizard는 하지 않는다.
- 빈번한 본문·표·폼을 모두 중앙 정렬하지 않는다. 참고 앱의 둥근 느낌은 유지하되 입력/결과는 왼쪽 정렬을 기본으로 한다.

## 4. 오늘 QT 장절이 안 나오는 문제의 해결 계획

### 4.1 확인된 원인과 미확인 영역

현재 실행 명령은 기본 프로필의 `mvn spring-boot:run`이었다. 이 설정은 `qt.acquisition.enabled=false`이며, `QtTodayService.resolve()`가 어댑터를 호출하기 전에 두 제공처에 다음 응답을 만든다.

```text
availabilityStatus = RANGE_NOT_PERMITTED
reasonCode         = PERMISSION_UNCONFIRMED
providerDate       = null
passage            = null
```

웹은 이 응답을 정상적으로 “자동 확인 안 함”으로 표시했다. 현재까지 확인된 원인은 **로컬 미리보기 실행 모드**다. 취득을 켠 뒤에도 두 제공처의 현재 HTML/날짜/인코딩을 잘 읽는지는 이 계획 작성 시점에 실서버로 검증하지 않았다. 스위치만 켜면 반드시 두 카드가 성공한다고 단정하지 않는다.

### 4.2 구현·검증 순서

1. **기존 실행 환경 확인**: 8081의 프로세스·프로필, `QT_ACQUISITION_ENABLED`, 제공처별 acquisition/disabled, `QT_TABLE_NAME` 유무를 확인한다. 비밀값을 출력하지 않는다. 로컬 시험은 메모리 저장소를 사용한다.
2. **실행 모드를 명시**: 루트에 `dev:qt:links`, `dev:qt:live`, `dev:web:api` 스크립트를 추가하고 README에 차이를 쓴다. 이 이름은 계획이며 현재 스크립트가 존재한다고 가정하지 않는다. `links`는 기본 프로필, `live`는 기존 `local-experiment`, 웹은 `VITE_QT_SOURCE=api`를 사용한다.
3. **로컬 자동 검증**: 기존 MockUpstream/fixture로 취득 on 시 RANGE_CONFIRMED, off 시 무요청, 제공처별 장애 격리, 서울 날짜 불일치, EUC-KR, 매일성경 보조 응답을 검사한다. 자동 테스트의 요청 대상은 계속 로컬 목 서버로 고정한다.
4. **개인 로컬 실취득 확인**: 이 계획을 구현하라는 후속 지시를 받으면 live 실행 동작을 설명하고 사용자가 선택한 실취득 실행 범위에서 기존 프로필을 사용한다. 이전 default 서버가 같은 포트를 점유한 채 남지 않게 소유 프로세스를 확인한다. 실제 요청 담당은 qt-local 한 명으로 한정한다. 기존 `smoke.sh` 승인 게이트를 우회하지 않는다.
5. **API에서 먼저 판정**: 서버의 `/api/qt/today`와 웹 프록시의 같은 경로를 확인한다. 성공이면 서울 오늘과 같은 `providerDate`, 비어 있지 않은 유효 `passage.ranges`, 공식 링크가 있어야 한다. 날짜를 2026-09-26으로 하드코딩하지 않는다.
6. **실패가 남을 때만 수정**: 상태·사유 코드에 따라 활성 프로필/override, 파싱 경로, 인코딩, 제공처 날짜를 점검한다. `NOT_COLLECTED_YET`라면 저장소 모드 유입 여부부터 본다. 확인된 결함을 본문 없는 최소 fixture로 재현하고 어댑터를 수정한다. 접근 제한은 우회하지 않는다.
7. **사용자 화면 정리**: 성공 카드에는 장절과 제공처 날짜를 우선 표시한다. 취득 off, 일시 오류, 오늘 게시 미확인을 구분한다. `providerDate=null`을 임의의 오늘 날짜로 채우지 않고, 날짜별 링크의 날짜는 “링크의 날짜”로 구분한다.
8. **결과 기록**: 설정 문제가 해결된 것과 두 제공처 실취득이 확인된 것을 별도로 기록한다. 한 제공처만 성공하면 다른 제공처는 원인과 공식 링크를 유지하고 “모두 해결”이라고 보고하지 않는다. 일반 공개·AWS 취득 설정은 별도 범위다.

현재 이미 있는 실행 경로(구현 후 README와 스크립트가 연결할 기준):


## 5. 놓치기 쉬운 회귀

- `activeTab === 'plan' && <PlanSection />`로 구현하면 왕복 시 입력이 사라진다. 패널의 안정적인 마운트를 유지한다.
- `opacity: 0`/`aria-hidden`만으로 숨기면 높이와 포커스 문제가 남는다. 실제 `hidden`을 사용한다.
- 일독 패널이 숨겨졌다고 계산 결과나 내보내기 모델을 초기화하지 않는다.
- 탭 전환을 브라우저 탭 전환으로 혼동하면 서울 자정 직후의 오래된 QT 노출을 놓친다. 활성화 직후 현재 날짜를 검사한다.
- 인쇄 CSS가 hidden 패널을 다시 보이게 하면 QT 화면에서 숨겨진 개인 계획이 인쇄될 수 있다. 상위 탭 UI는 인쇄에서 숨기고, 일독 탭의 인쇄 버튼은 현재 계획표만 출력하게 한다. QT 탭에서 브라우저 인쇄를 호출해도 숨겨진 일독 계획을 강제로 출력하지 않는다.
- `getByText`는 숨겨진 DOM까지 찾을 수 있다. 화면 분리 검증은 role/visibility/키보드 접근을 기준으로 한다.
- 기존 App 통합 테스트 일부는 두 영역이 항상 보인다고 가정한다. 테스트를 지우거나 일괄 `hidden:true`로 바꾸지 말고 실제 사용자처럼 일독 탭을 선택한 후 검증한다.
- 별도 계산 성능 검증과 무작위 3,000건 테스트는 보존한다. CI 타임아웃 수정 커밋 `264c3f7`의 해당 테스트 15초 제한을 되돌리지 않는다.

## 6. 검증과 완료 기준

| ID | 검증 시나리오 | 통과 조건 |

주요 수정 대상 테스트: `QtToday.test.tsx`, `PlanSection.test.tsx`의 App 통합 부분, `noStorage.test.tsx`, `defaultData.test.tsx`, `a11y.test.tsx`. `QtFreshness.test.tsx`에 내부 탭 복귀를 추가하고 새 `ServiceTabs.test.tsx`/`AppTabs.test.tsx`에 탭·왕복·비가시 상태를 검증한다. `NoticesDialog`, 내보내기·인쇄 테스트도 회귀 대상으로 확인한다.

브라우저 검증 증거: 두 탭 각각의 모바일/데스크톱 캡처, 입력 왕복 보존, 키보드 전환, 인쇄 미리보기, 한영·다크 상태를 `docs/qa/UI-tabs-review.md`에 기록한다. 정적/단위 테스트 통과를 실취득·실브라우저 검증 완료로 대신하지 않는다.

## 7. 구현 순서

1. lead가 파일 소유권, 위 DOM 계약, `QtToday` 활성 상태 전달 방식, 토큰 이름을 확정해 팀원에게 전달한다.
2. shell-state(탭·상태), visual(스타일·표시 구조), qt-local(실행 경로·장절 진단)을 병렬 진행한다.
3. lead가 통합하고 기존 App 테스트의 새 진입 경로를 확인한다.
4. qa가 독립적으로 UI/QT 검증표를 작성한다. 결함은 해당 파일 소유자에게 돌려 수정한다.
5. lead가 필요한 검증을 확인하고 사용자에게 변경 파일·실행 주소·실취득 결과·남은 문제를 보고한다. 이번 문서 작성만으로 구현 완료나 커밋·푸시를 선언하지 않는다.
