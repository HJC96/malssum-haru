## 1. 사용자 흐름

상위 탭은 `오늘의 QT`와 `일독 계획`으로 유지한다. QT 탭을 열면 다른 큐티 사이트를 먼저 골라 들어가는 대신 오늘 콘텐츠를 바로 읽는다.

```text
오늘의 QT
  오늘의 말씀 · 2026-09-27
  ┌ 구약 ─ 성경 구절 한 절 ─ 짧은 해설 ┐
  └ 신약 ─ 성경 구절 한 절 ─ 짧은 해설 ┘
  [매일성경 바로가기] [생명의삶 바로가기]
일독 계획
```

- 날짜는 서울 시간 기준으로 하루에 한 번 정하고, 새로고침이나 언어 변경으로 그날 구절이 바뀌지 않는다.
- 두 구절은 각각 하나의 번역본에서 실제로 확인된 한 절을 표시한다. 책·장·절, 번역본, 출처를 바로 가까이 적는다.
- 해설은 각 구절 아래에 제공한다. 2~4문장의 짧은 문맥 설명을 기본으로 하고, 성경 본문 인용과 구별해 표시한다.
- 두 공식 바로가기는 콘텐츠 아래에 동등한 버튼으로 둔다. 기본값은 현재 정해 둔 공식 URL이며, QT 범위 크롤링/API 취득은 새 화면에 필요하지 않다.
- 탭 이름·기존 상위 탭 상태 보존·일독 계획 입력 상태는 유지한다. QT 패널 안의 섹션 제목은 `오늘의 말씀`으로 바꾼다.
- `omalssum-react`에서 참고할 요소는 중앙의 둥근 흰 카드, 옅은 파란색 면, 인디고 버튼, 말씀→해설의 읽기 순서다. 무작위 구절 API, 임시 고정 문장, 외부 이미지 API는 사용하지 않는다.

## 2. 번역본과 본문 사용 선행 조건

이번 변경은 QT 제공처가 게시한 범위를 링크로 안내하던 기존 정책에서, 선택한 번역본의 말씀 두 절을 화면에 표시하는 것으로 범위를 넓힌다. 기존 PRD의 `본문 미표시` 결정은 이 두 절 표시 정책으로 대체한다.

- 사용자는 번역을 하지 말고 개역한글판을 사용하라고 결정했다. 대한성서공회 저작권 FAQ는 개역한글판의 저작재산권 보호기간 경과 및 저작권료 없이 사용 가능함을 안내하면서, 성명표시권과 동일성유지권 준수를 요구한다. 성경플랫폼 저작권 표기에는 `성경전서 개역한글판 © 대한성서공회 1961`로 되어 있다. 따라서 UI에는 정확한 역본·저작권자를 밝히고 본문을 현대화·수정하지 않는다.
- `web/public/daily-word/2026-09-26.json`에는 개역한글판 시편 23:1, 요한복음 3:16 원문과 별도 편집 해설을 담았다. 인용문은 CrossWire KorRV 모듈(1952/1961, 배포 라이선스 Public Domain, Wikisource 출처) 및 그 전사본과 대조했다. 자료는 정확한 단일 절만 포함하고 저작권자·역본 출처를 가까이 표시한다.
- 후보의 이용 근거가 화면 표시와 정적 콘텐츠 배포를 명확히 뒷받침하지 않으면, 본문 파일·해설 콘텐츠를 리포지터리나 공개 저장소에 넣지 않는다. `docs/data-sources.md`와 `docs/rights-matrix.md`에 근거·출처·검토일을 남긴 뒤 실제 본문을 채운다.
- 영어 UI를 제공할 경우 한국어 구절을 임의 번역해 성경 본문처럼 보이지 않는다. 영어 번역본과 그 사용 조건을 별도로 선택하거나, 영어 화면에서 한국어 본문을 번역본 라벨과 함께 제공할지 제품 결정을 기록한다.
- 원문 구절은 모델이 생성하지 않는다. 승인된 자료에서 정확히 한 절을 읽어 렌더링하고, 자동 생성 설명이 원문을 다시 출력하거나 긴 문구를 인용하지 않게 한다.
- 본문 자료 선택이 끝나기 전에도 카드·날짜·오류·바로가기 UX는 출처를 표시한 명시적 개발 fixture로 구현할 수 있다. fixture는 실제 콘텐츠, 권리 확인, 정확한 당일 결과로 오인되지 않도록 명확히 분리한다.

## 3. 오늘 콘텐츠 데이터 계약 초안

일자별 응답/파일은 하나의 날짜와 버전으로 두 카드를 함께 제공한다. 한 카드만 갱신돼 두 날짜 콘텐츠가 섞이지 않게 원자적으로 검증한다.

```json
{
  "schemaVersion": "1",
  "date": "2026-09-27",
  "timeZone": "Asia/Seoul",
  "contentVersion": "daily-word-2026-09-27-v1",
  "oldTestament": {
    "reference": { "bookId": "...", "chapter": 1, "verse": 1 },
    "translationId": "...",
    "textLanguage": "ko",
    "text": "...",
    "explanation": { "text": "...", "kind": "reviewed", "language": "ko" },
    "source": { "name": "...", "url": "..." }
  },
  "newTestament": { "...": "같은 구조" }
}
```

- 두 항목은 각각 구약/신약 책에 속하고 reference는 정확히 한 절이어야 한다.
- `text`는 선택 번역본의 정확한 원문, `explanation`은 별도 작성된 설명이다. 둘의 언어를 UI 언어와 독립적으로 명시해 화면 낭독기가 실제 텍스트 언어를 따르도록 한다. 로컬 시편 절 수 테이블처럼 다른 판본의 자료로 절 존재 여부를 추측하지 않는다.
- 프로덕션 validation은 승인 레지스트리에 등록된 번역본만 허용한다. 테스트용 허용 플래그는 테스트 fixture에 한정하며 프로덕션 로더의 기본값은 비활성이다.
- 날짜·번역본·출처·설명 버전을 추적해 오류가 나면 당일 artifact만 교체할 수 있게 한다.
- 누락·날짜 불일치·잘못된 구절·출처 정보가 있는 경우 검증을 실패시킨다. 전날 구절을 오늘 자료처럼 보여 주지 않고, 본문/해설 실패 상태와 공식 바로가기를 제공한다.
- 두 카드에 사용한 구절과 해설은 내보내기·일독 진도 입력·사용자 개인정보와 무관하다. 개인 기록이나 답변을 API에 보내지 않는다.

## 8. 후보 풀 기반 말씀 선택 및 원리 안내 (2026-09-27 계획 추가)

### 현재 상태와 목표

- 현재 구현은 `/daily-word/YYYY-MM-DD.json`에 날짜별로 미리 검토해 넣은 구약 한 절·신약 한 절을 불러온다. 공개 브라우저에서 무작위 선택을 하지 않으며, 현재 자료는 2026-09-26 하루치뿐이다.
- 다음 단계에서는 승인된 개역한글판 본문과 해설 검토가 완료된 구절을 각각 구약 후보 풀과 신약 후보 풀로 구성한다. 후보 풀이 준비되기 전까지 현행 날짜별 artifact 동작을 유지하고 화면에서 무작위라고 설명하지 않는다.
- 사용자가 말한 `구약 후보 1,000절, 신약 후보 2,000절`은 설명을 위한 예시 수다. 실제 N은 본문 사용 근거와 해설 검수가 끝나 실제 공급 가능한 후보 수로 계산하며, 전체 성경의 절 수와 혼동하지 않는다.

### 화면 설명

- `오늘의 QT` 카드의 하단 한쪽에 `오늘의 말씀은 어떻게 골랐나요?` 정보 아이콘/링크를 둔다. 데스크톱은 hover와 keyboard focus로 팝오버를 열고, 모바일에서는 탭으로 같은 내용을 연다. 화면 가장자리에 잘리거나 본문·해설과 혼동되지 않도록 카드 안에 배치한다.
- 후보 풀 추첨이 실제로 배포된 뒤 설명 문구는 다음 내용을 담는다: “오늘의 구절은 준비된 후보에서 구약·신약 각각 하나씩 같은 확률로 선택합니다. 예를 들어 구약 후보가 1,000절이면 각 절은 1/1,000, 신약 후보가 2,000절이면 각 절은 1/2,000 확률로 선택됩니다. 같은 날짜에는 새로고침해도 구절이 바뀌지 않습니다. 다른 날짜에 이전 구절이 다시 나올 수 있습니다.”
- 실제 후보 수를 제품에 공개하는 경우 고정된 예시값을 쓰지 않고, 공개 artifact와 같은 `poolVersion`에 기록된 검증 수치를 표시한다. 풀 크기나 선택 정책이 바뀌면 안내도 같은 릴리스에서 갱신한다.
- 한국어/영어 설명을 함께 검수한다. hover 전용 구현은 금지하고, 포커스/탭/스크린리더에서 열고 닫을 수 있도록 `button`과 연결된 `aria-describedby` 또는 접근 가능한 disclosure를 사용한다.

### 선택 데이터와 추출 방식

1. **후보 준비**: 승인된 번역의 정확한 단일 절만 구약/신약 후보로 분리한다. 후보 항목은 안정적인 ID, `bookId/chapter/verse`, 원문, 번역본 ID, 출처 검증 상태, 검토된 짧은 해설 버전을 가진다. 해설 없는 절은 후보에서 제외한다.
2. **균등 선택**: 각 날짜에 `oldTestament`와 `newTestament`를 서로 독립적으로 선택한다. 각 풀의 모든 후보를 같은 가중치로 취급하므로 풀 크기가 `N`일 때 한 번의 추첨에서 각 후보의 선택 확률은 `1/N`이다. 예시 풀 1,000/2,000이면 각각 1/1,000, 1/2,000이다.
3. **날짜 고정**: 생성 작업은 `Asia/Seoul` 날짜 + 알고리즘 버전 + 풀 버전으로 추출 seed를 고정해 같은 날짜 artifact를 재현할 수 있게 한다. 정수 범위에서 인덱스를 고를 때 modulo 편향이 생기지 않도록 rejection sampling 등 unbiased mapping을 쓴다. 브라우저 새로고침/언어 변경 시 재추첨하지 않는다.
4. **중복 정책**: 첫 버전은 매일 독립 추첨으로 구현하며 서로 다른 날짜 사이 반복 선택은 허용한다. 날짜 중복은 같은 artifact로 방지된다. 반복 빈도가 높다는 사용자 근거가 모일 경우에만 최근 이력 제외 정책을 별도 결정하며, 그 경우 후보 수 N과 1/N 안내를 날짜별 유효 풀 기준으로 다시 설명한다.
5. **정적 게시**: 선택기는 배포/콘텐츠 생성 단계에서 실행하고 결과의 완전한 말씀·해설을 기존 날짜 artifact에 써서 검증·승인한 뒤 정적 호스팅한다. 사용자 브라우저에서 전체 구절 코퍼스를 무작위 탐색하거나, 매 페이지 요청 때 외부 API/LLM을 호출하지 않는다.
6. **버전·감사**: 생성 manifest에 알고리즘 버전, 후보 풀 버전/크기, 날짜 seed 식별자, 구절 ID, 검토 상태를 둔다. seed 원문이나 개인정보는 저장하지 않는다. 재생성 시 해당 날짜 artifact를 원자적으로 교체하고 이전 버전/검토 이력을 남긴다.

### 단계와 검수

- DW-R01 권리/정본 확인: 개역한글판 사용 조건, 정확한 전수 본문 자료, 책·장·절/절 번호 체계의 출처와 날짜별 정적 공개 가능 여부를 확인한다. 조건이 불확실한 전집 자료를 후보 풀에 넣지 않는다.
- DW-R02 후보 카탈로그: 개역한글판 후보 데이터의 provenance, testament 분류, 단일 절, reference, 중복 ID, 본문 무결성 및 해설 검토를 자동 검사한다. 단순히 현재 일독 계획용 잠정 장절 수 표를 본문 검증 근거로 재사용하지 않는다.
- DW-R03 결정론적 추출기: 날짜·poolVersion·algorithmVersion 입력만 받는 순수 생성기로 구약/신약의 독립 선택, 동일 날짜 재현, 범위 경계, unbiased index mapping을 테스트한다.
- DW-R04 artifact 통합: 추출 결과를 기존 스키마의 당일 JSON으로 만들고 기존 validator/loader 및 원자적 배포 검증을 통과시킨다. 실패 시 현행 자료를 다른 날짜 콘텐츠로 대체하지 않는다.
- DW-R05 설명 UX: 카드 하단 정보 팝오버, 모바일 탭, 키보드 포커스, 스크린리더, 한/영 및 화면 가장자리 위치를 검수한다. 실제 추첨이 제품 코드와 공개 artifact에서 활성화되기 전엔 확률 설명을 배포하지 않는다.
- DW-R06 QA/운영: 후보 풀 크기가 바뀌는 경우 일별 공개 텍스트와 생성 버전이 일치하는지, 동일 날짜 출력이 안정적인지, 날짜별 선택 분포가 장기간 균등에 가까운지 seed 수천 개를 이용해 통계 검사한다. 통계 검사는 작은 표본 오차를 허용하고, 단일 일치/불일치만으로 알고리즘 실패를 판정하지 않는다.

무작위 선택은 현재 코드에 구현되어 있지 않다. 본문 전집의 사용 근거, 충분한 검토 해설 후보, 재현 가능한 선택기, 데이터 QA가 준비된 뒤 이 절차를 공개 배포한다. 그 전에는 하루치 수동 검토 artifact와 당일 자료 없음 상태를 유지한다.

## 4. 구현 경로와 서비스 경계

### 첫 출시 데이터 제공

- QT 제공처를 매 요청 때 불러오는 방식 대신, 검토된 날짜별 콘텐츠 artifact를 만들어 정적 호스팅에서 읽는다. 기존 S3/CloudFront 자산 흐름을 먼저 활용해 요청 시 지연과 운영 서비스를 늘리지 않는다.
- 웹에는 `DailyWord` 로더/응답 검증기를 두고 앱은 테스트 가능한 인터페이스에 의존한다. 로컬·테스트는 명시적 fixture, 공개 빌드는 해당 날짜의 실제 artifact만 사용한다.
- 날짜 선택, 구약/신약 분류, 한 절 검증, 번역본·출처 유효성은 생성 단계에서 검사한다. 조회 실패는 카드 영역에서 처리하고 바로가기는 계속 사용할 수 있다.
- 당일 콘텐츠는 미리 준비해 공개한다. 초기에는 전체 365일 본문·해설을 한 번에 생성하거나 게시하지 않고, 검토 가능한 짧은 일정(예: 30일)을 기준으로 공급 운영을 정한다.

### 생성·서버리스·Spring 학습

- 현재 `services/ai`는 WEB 본문을 전제로 한 비활성 골격이다. 이를 개역한글판 본문 설명에 연결하거나 실시간 AI 설명을 제공한다고 가정하지 않는다.
- 이후 생성 자동화는 API 키·비용 한도·번역본/절 대응·해설 품질 검토 절차가 준비되면 EventBridge 일정 + Lambda 작업 + S3 artifact 저장으로 별도 구성한다. 실패해도 마지막 승인된 자료를 정확한 날짜에만 제공하고, 새 설명을 몰래 대체하지 않는다.
- Spring Cloud는 `daily-content`와 `explanation` 계약, Circuit Breaker, 모의 설명 제공을 로컬 실습으로 이어간다. 대시보드의 정적 콘텐츠 읽기를 위해 Gateway/Eureka를 필수 운영 구성으로 추가하지 않는다.
- 이 일일 선택 기능은 기존 `/api/qt/today`에서 제공처 범위를 조회하는 것과 다른 도메인이다. 기존 QT 어댑터·계약·권리 기록을 새 콘텐츠 데이터의 출처 승인으로 오해하지 않는다.

## 5. 바로가기 동작

- 기존 `officialLinks.ts`의 매일성경·생명의삶 공식 URL과 새 탭/접근성 정책을 재사용한다.
- 버튼은 각 공식 서비스로 직접 연결하고 별도 중간 서버를 거치지 않는다. 날짜 지정 주소가 이미 명시된 서비스만 해당 URL을 사용하고, 오늘 페이지는 버튼의 설명에 날짜가 바뀔 수 있음을 표시한다.
- 바로가기 클릭은 일독 범위나 진도에 반영하지 않는다. 성경 한 절 카드의 출처와 외부 QT 버튼의 목적을 서로 혼동하지 않게 라벨을 분리한다.

## 6. 작업 단계와 멀티 에이전트 팀

계획 확정 이후 GPT-6 Luna 팀으로 구현한다. lead 포함 최대 4개 세션을 사용하고 파일 소유권을 나눈다.

| 순서 | 담당 | 소유 범위 | 작업 |
| --- | --- | --- | --- |
| W01 | lead + source-rights | `docs/data-sources.md`, `docs/rights-matrix.md`는 담당자만; `docs/PRD.md`는 lead | KBS 공식 저작권 FAQ와 CrossWire KorRV 배포 조건 확인; 개역한글판 원문 사용, 저작자 표시·원문 동일성 유지 |
| W02 | content-data | 신규 `web/public/daily-word/**`, loader/validator | 날짜 artifact와 승인 번역 레지스트리, exact-date·single-verse 오류 검사 |
| W03 | daily-ui | `web/src/app/dailyWord/**`, 신규 `web/src/components/dailyWord/**`, `styles/daily-word.css` | 두 절 카드, 로딩/오늘 자료 없음/오류, 날짜, 하단 공식 버튼 구성 |
| W04 | lead + platform-cost/msa-lab | 루트 화면·i18n·CDK·`labs/spring-cloud/**`는 각 owner와 협의 | static source 연결, bilingual/SEO/cache 전략, 후속 Lambda 흐름을 계약 수준에서 확인. 서버리스 자원은 기존 비용 상한 검토 전 배포하지 않음 |
| W05 | qa + lead | `docs/qa/daily-word-review.md`, lead는 공통 통합 | 날짜 경계, 구약/신약 검증, 링크 fallback, 화면·접근성·언어·새로고침 및 회귀 확인 |

병렬화 전에 W01의 콘텐츠 사용 조건과 W02/W03의 JSON/UI 계약을 lead가 정한다. W01은 실제 외부 출처 본문 다운로드 없이 공식 권리/라이선스 문서와 기존 조사 자료로 근거를 확인하는 단계부터 시작한다. 저작권자에게 연락·계정 생성·비용이 필요한 작업은 별도 작업 요청으로 다룬다.

## 7. 완료 기준

- D-01: 자료가 준비된 날짜에는 기본 탭에서 구약 한 절, 신약 한 절 및 각 해설을 읽을 수 있다. 날짜는 서울 기준이며 누락일엔 이전 본문을 대신 표시하지 않는다. 현재 자료는 2026-09-26 하루치다.
- D-02: 본문은 `개역한글판 (1961)` 및 `성경전서 개역한글판 © 대한성서공회 1961`로 표시한다. 본문을 번역·현대화하지 않고, 구절 출처와 편집 해설을 분리해 표시한다.
- D-03: 어느 본문도 무작위 외부 API나 모델 출력에서 직접 가져오지 않는다. 구약·신약 classification, single-verse integrity, `date`, `timeZone`, version을 자동 검증한다.
- D-04: 매일성경·생명의삶 버튼은 공식 URL로 직접 열린다. 두 제공처 범위 자동 조회가 없어도 메인 말씀을 볼 수 있다.
- D-05: 자료 누락·오류·시간대 경계가 구체적으로 안내되며 전날 자료를 오늘로 위장하지 않는다. 바로가기는 오류 때도 쓸 수 있다.
- D-06: 한/영 표시, 모바일·데스크톱, 키보드·스크린리더, 다크모드와 출처 표기를 검수하고 결과를 남긴다.
- D-07: QT 탭으로 방문한 페이지와 일독 계획 계산·진도 사이에 데이터가 공유되지 않는다. 새로고침 후 개인 진도는 기존대로 복원되지 않는다.
- D-08: 정적 hosting 단계는 기존 AWS 자산에서 확인하고, 일일 Lambda 자동화나 Spring Cloud를 공개 운영 경로에 포함하려면 비용·장애 경계·보호 키 관리를 별도 검수한다.

### 이번 계획에 포함하지 않는 것

- 매일성경·생명의삶 본문을 자동 크롤링하거나 그 해설을 가져오는 기능.
- 두 절을 합친 본문 전체 검색, 묵상 답변 저장·공유, 사용자별 구절 추천.
- 웹 페이지에 무작위 구절 API나 교체되는 placeholder 본문을 두는 것.
- 사용자 확인 없이 실제 LLM·제3자 API 키를 사용하거나 AWS에 배포하는 일.
- 기존 MSA 실습을 production gateway나 사용자 화면의 필수 경로로 전환하는 것.
